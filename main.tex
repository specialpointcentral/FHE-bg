\begin{frame}{1.1 Motivation and Definition of FHE}
  \begin{itemize}
    \item \textbf{Reality tension:} data must be ``used'' without ever being ``seen''.
    \begin{itemize}
      \item Cloud outsourcing: model inference, statistical analytics, search indexing.
      \item Regulatory pressure: GDPR, HIPAA, and cross-border data controls.
      \item Traditional encryption covers storage and transit, but requires decryption for computation.
    \end{itemize}
    \item \textbf{Privacy-computing goal:} make data usable while keeping it confidential.
    \begin{itemize}
      \item Servers only handle ciphertext yet complete the agreed computation.
      \item Clients decrypt and recover the same outcome as plaintext evaluation.
    \end{itemize}
    \item \textbf{FHE definition:} core property $\Dec(f(\Enc(x))) = f(x)$.
    \begin{itemize}
      \item Meaning: homomorphic $f$ on ciphertext, decrypt for the plaintext result.
    \end{itemize}
    \item \textbf{Typical applications:}
    \begin{itemize}
      \item Healthcare: encrypted imaging or genomics analysed in the cloud, hospitals decrypt locally.
      \item Finance: encrypted transactions scored for risk or collaborative anti-fraud.
      \item Privacy smart contracts: on-chain ciphertexts with off-chain/on-chain FHE execution.
    \end{itemize}
  \end{itemize}
  \note{On this slide I explain why we need to compute on encrypted data. In many real systems, data must be used but cannot be seen in plaintext. Examples include cloud outsourcing for model inference, statistics, and search, under strong rules like GDPR and HIPAA and cross-border controls. Traditional encryption protects data in storage and in transit, but for computation we usually decrypt first, and that step is risky. The goal of privacy-preserving computing is to let the server work only on ciphertexts, while the client later decrypts the final result and gets the same answer as if we had used plaintext. The core FHE property shown here is $\Dec(f(\Enc(x))) = f(x)$ [read: “Dec of f of Enc of x equals f of x”]. Here $\Enc$ means encryption, $\Dec$ means decryption, and $f$ is the same function on plaintext and ciphertext. Typical applications include privacy-preserving healthcare analytics, finance and anti-fraud on encrypted transactions, and privacy smart contracts where ciphertexts live on chain but computation can still happen.}
\end{frame}

\begin{frame}{1.2 Evolution of Fully Homomorphic Encryption}
  \begin{itemize}
    \item 2009: Gentry's breakthrough first-generation scheme based on ideal lattices.
    \item 2011--2014: Second generation (BGV, BFV) improves efficiency via leveled FHE and bootstrapping optimizations.
    \item 2016: CKKS introduces approximate arithmetic for real-number workloads such as machine learning inference.
    \item 2016+: TFHE enables fast gate-by-gate Boolean computation with rapid bootstrapping.
    \item Current landscape: hybrid approaches, GPU acceleration, and practical libraries (HElib, SEAL, Concrete, OpenFHE).
  \end{itemize}
  \note{Here I give a short history of FHE. In 2009, Gentry proposed the first FHE scheme using ideal lattices. It was a big theoretical breakthrough but very slow. Between 2011 and 2014, second-generation schemes such as BGV and BFV appeared; they introduced leveled FHE and more efficient bootstrapping, so performance improved. In 2016, the CKKS scheme was introduced to support approximate arithmetic on real and complex numbers, which is very useful for machine learning inference and numerical analytics. Around the same time, TFHE appeared, focusing on fast Boolean gates with efficient per-gate bootstrapping, which is good for comparisons, branching, and verification logic. Today we have practical libraries like HElib, SEAL, Concrete, and OpenFHE, and there is a lot of work on GPUs and hardware acceleration. In this talk we use CKKS and TFHE as two important representatives.}
\end{frame}

\section{Mathematical Foundations of FHE}

\begin{frame}{2. Mathematical Foundations Overview}
  \begin{itemize}
    \item Modular arithmetic and polynomial rings ($\mathbb{Z}_q$, $R_q$) as the container for ciphertext addition/multiplication.
    \item Batched (SIMD) encoding intuition: one encrypted polynomial carries many data slots.
    \item Hardness assumptions from LWE/RLWE tying noisy linear equations to ring-based constructions.
  \end{itemize}
  \note{Now we move to the mathematical foundations of FHE. There are three key ingredients. First, modular arithmetic and polynomial rings like $\mathbb{Z}_q$ and $R_q$ [read: “Z sub q” and “R sub q”]. These rings give us a space where we can do both addition and multiplication on ciphertexts. Second, batched or SIMD encoding: one encrypted polynomial can carry many data slots in parallel so homomorphic operations are vectorized. Third, the security assumptions LWE and RLWE, which say that solving certain noisy linear equations is hard. Modern FHE schemes build on these problems and inherit their hardness. In the next slides we look at each ingredient in more detail.}
\end{frame}

\begin{frame}{2.1 Modular Arithmetic and Polynomial Rings}
  \begin{itemize}
    \item Modern FHE schemes encode ciphertexts as polynomials over rings to support both addition and multiplication (ring = additive group + multiplicative semigroup).
    \begin{itemize}
      \item Concrete example: a clock with 12 hours. The numbers on the clock are $0, 1, \dots, 11$, and $9 + 5 \equiv 2 \pmod{12}$ because the sum wraps around.
    \end{itemize}
    \item Integer modular ring: $\mathbb{Z}_q = \{0,1,\dots,q-1\}$ with addition/multiplication taken mod $q$ (typically a large prime or an RNS prime chain).
    \item Polynomial ring: $R_q = \mathbb{Z}_q[x]/(x^N+1)$ with $N$ usually a power of two.
    \begin{itemize}
      \item Elements are polynomials of degree $< N$ with coefficients in $\mathbb{Z}_q$.
      \item Multiplication: convolve coefficients, then reduce by $(x^N+1)$ so $x^N \equiv -1$.
    \end{itemize}
  \end{itemize}
  \note{Before we go to the abstract symbols, let me start with a concrete example. Think about a clock with 12 hours. The numbers on the clock are $0, 1, \dots, 11$. If I add $9$ and $5$, I get $14$, but on the clock this wraps around to $2$. We write this as $9 + 5 \equiv 2 \pmod{12}$. This is modular arithmetic: we keep the result inside a fixed set by wrapping around. Now we generalize this idea. Modern FHE does not work over plain integers; instead it uses rings that support both addition and multiplication. The first abstract example is the integer modular ring $\mathbb{Z}_q$ [read: “Z sub q”]. It is the set of numbers $0, 1, \dots, q - 1$, with addition and multiplication taken modulo $q$, where $q$ is usually a large prime or part of an RNS chain. The second example is the polynomial ring $R_q = \mathbb{Z}_q[x]/(x^N+1)$ [read: “R sub q equals Z sub q of x, modulo x to the N plus one”]. Here $N$ is usually a power of two. Elements in this ring are polynomials of degree less than $N$ with coefficients in $\mathbb{Z}_q$. When we multiply two polynomials, we convolve the coefficients and then reduce modulo $x^N+1$, which effectively forces $x^N$ to behave like $-1$. These polynomial rings are the container for ciphertexts in many FHE schemes.}
\end{frame}

\begin{frame}{2.2 Intuition for Batched (SIMD) Encoding}
  \begin{itemize}
    \item Goal: start from a complex vector\\
      $$z = (z_1, z_2, \dots, z_{N/2}) \in \mathbb{C}^{N/2},$$
      encode it into the CKKS ring $R_q = \mathbb{Z}_q[x]/(x^N+1)$.
    \item Observation: when $N$ is a power of two, there is an approximate isomorphism\\
      $$R_q \otimes \mathbb{C} \cong \mathbb{C}^{N/2},$$
      so one ciphertext carries $N/2$ complex slots.
    \item Practical encoding: run the complex-domain inverse DFT (discrete Fourier transform) to map slots into polynomial coefficients\\
      $$m(x) = \mathrm{Inverse\text{-}DFT}(z),$$
      then scale and round to obtain an integer polynomial $\tilde{m}(x)$ before reducing modulo $q$, so $\tilde{m}(x) \bmod q \in \mathbb{Z}_q[x]$.
  \end{itemize}
  \note{Now we look at the idea of batching, or SIMD encoding. The goal is to pack a whole vector of complex numbers into one polynomial. Suppose we start from a complex vector $z = (z_1, z_2, \dots, z_{N/2})$ in $\mathbb{C}^{N/2}$. Here $z_1$ [read: “z one”] is the first coordinate, and $\mathbb{C}^{N/2}$ [read: “C to the N over two”] is the ambient space. When $N$ is a power of two, there is an approximate isomorphism $R_q \otimes \mathbb{C} \cong \mathbb{C}^{N/2}$. You can think of this as saying: one polynomial in the ring corresponds to $N/2$ complex slots. To encode, we run an inverse discrete Fourier transform, or inverse DFT, from the vector $z$ to a polynomial $m(x)$. Then we scale and round the coefficients to get an integer polynomial $\tilde{m}(x)$ [read: “m tilde of x”]. Finally, we reduce the coefficients modulo $q$ so the polynomial lies in $\mathbb{Z}_q[x]$. The key idea is that one ciphertext holds many slots, so FHE operations act on whole vectors at once.}
\end{frame}

\begin{frame}{2.3 LWE and RLWE}
  \begin{itemize}
    \item Motivation: Learning With Errors (LWE) and Ring-LWE (RLWE) provide computationally controllable, provably secure public-key and homomorphic encryption foundations.
    \item Core idea: add random noise to hide plaintexts while preserving ring/polynomial structure for computation, reducing security to GapSVP (quantum-resistant).
    \item LWE (vector form): samples $(A, b = A \seckey{s} + e \bmod q)$ where $A$ is random, $\seckey{s}$ secret, $e$ small noise.
    \item RLWE (polynomial form): samples $(a(x), b(x) = a(x) \seckey{s(x)} + e(x) \bmod q)$ over $R_q$.
    \item Transition: RLWE inherits LWE hardness while enabling structured polynomials that FHE schemes rely on.
  \end{itemize}
  \note{Now I introduce the LWE and RLWE assumptions, which provide the hardness foundations for FHE schemes. The main idea is to hide the secret message by adding small random noise, while still keeping enough algebraic structure for computation. The hardness of LWE and RLWE is related to lattice problems like GapSVP, and these are believed to be hard even for quantum computers. In LWE, we work with vectors and matrices over $\mathbb{Z}_q$. Samples look like $(A, b)$, where $b = A \seckey{s} + e \bmod q$ [read: “b equals A times s plus e, modulo q”]. Here $A$ is a random matrix, $\seckey{s}$ is a secret vector, and $e$ is small noise. In RLWE, we move to polynomials. Samples look like $(a(x), b(x))$, where $b(x) = a(x)\seckey{s(x)} + e(x) \bmod q$ [read: “b of x equals a of x times s of x plus e of x, modulo q”]. Now everything lives in the polynomial ring $R_q$. RLWE keeps the hardness of LWE, but it fits much better with polynomial-based FHE schemes, and most ring-based constructions rely on RLWE.}
\end{frame}

\begin{frame}{2.4 LWE: Key Generation, Encryption, Decryption}
  \begin{description}
    \item[Key generation] Sample $\seckey{s} \leftarrow \mathbb{Z}_q^n$, noise $e \leftarrow \mathbb{Z}_q^n$, and public randomness $A \leftarrow \mathbb{Z}_q^{n \times n}$. Set
    $$
      b = A \seckey{s} + e \pmod{q}.
    $$
    Publish $(A, b)$; keep $\seckey{s}$ secret.
    \item[Encryption of $\plaintext{m} \in \{0,1\}$] Pick a small random vector $r$, then compute
    \[
      c_0 = A^\top r,\qquad
      c_1 = b^\top r + \Delta \plaintext{m},
    \]
    forming ciphertext $\boxed{c = (c_0, c_1)}$,
    where the scaling constant is $\Delta = q/2$ for a binary alphabet (or $q/L$ for $L$ equally spaced levels). As a quick sanity check, let $r = \mathbf{1}$ so $c_0$ simply sums the columns of $A$.
    \item[Decryption with $\seckey{s}$] Evaluate
    \[
      c_1 - c_0^\top \seckey{s} = e^\top r + \Delta \plaintext{m}.
    \]
    Because $e^\top r$ is tiny, we recover the message by normalizing and rounding:
    $$
      \widehat{m} = \operatorname{round}\!\left(\frac{c_1 - c_0^\top \seckey{s}}{\Delta}\right),
    $$
    which snaps back to the original $\plaintext{m}$.
  \end{description}
  \note{Here we see the full LWE workflow: key generation, encryption, and decryption. For key generation, we pick a secret vector $\seckey{s}$ in $\mathbb{Z}_q^n$ [read: “Z sub q to the n”], sample a noise vector $e$, and a random public matrix $A$ in $\mathbb{Z}_q^{n \times n}$. Then we compute $b = A \seckey{s} + e \bmod q$. The pair $(A, b)$ is the public key and $\seckey{s}$ is the secret key. To encrypt a bit $\plaintext{m} \in \{0,1\}$, we pick a small random vector $r$ and compute $c_0 = A^\top r$ and $c_1 = b^\top r + \Delta \plaintext{m}$ with $\Delta = q/2$ [read: “Delta equals q over two”]. The ciphertext is $(c_0, c_1)$. To decrypt, we compute $c_1 - c_0^\top \seckey{s}$, which equals $e^\top r + \Delta \plaintext{m}$ and is very close to either $0$ or $\Delta$. Finally we divide by $\Delta$ and round to get back $\plaintext{m}$. The key point is that small noise hides the bit but does not break decryption.}
\end{frame}

\begin{frame}{2.5 RLWE: $b(x) = a(x)s(x) + e(x) \pmod{q}$}
  \begin{description}
    \item[Ring setting] Work in $R_q = \mathbb{Z}_q[x]/(x^N+1)$ with secret $\seckey{s(x)}$ and small error $e(x)$ drawn from a narrow distribution on $R_q$.
    \item[Key generation] Sample public $a(x) \leftarrow R_q$, draw $e(x)$, and set
    \[
      b(x) = a(x)\seckey{s(x)} + e(x) \pmod{q}.
    \]
    Publish $(a(x), b(x))$, keep $\seckey{s(x)}$ secret.
    \item[Encryption of plaintext $\plaintext{m(x)} \in R_q$] Pick a small, sparse $r(x)$ (conceptually set $r(x)=1$ to sanity-check the formulas) and output
    \[
      c_0(x) = a(x) r(x), \qquad
      c_1(x) = b(x) r(x) + \Delta \, \plaintext{m(x)},
    \]
    with $\Delta = q/t$ for $t$ plaintext slots (e.g., $t=2$ for binary messages), then package $\boxed{c(x) = (c_0(x), c_1(x))}$.
    \item[Decryption] Compute
    \[
      c_1(x) - c_0(x) \seckey{s(x)} = \Delta \, \plaintext{m(x)} + \widetilde{e}(x),
    \]
    divide by $\Delta$, and round coefficient-wise to strip the small noise.
  \end{description}
  \note{Now we lift LWE into the ring setting, which gives RLWE. We work in the ring $R_q = \mathbb{Z}_q[x]/(x^N+1)$ [read: “R sub q equals Z sub q of x, modulo x to the N plus one”]. The secret key is a polynomial $\seckey{s(x)}$ with small coefficients, and the noise $e(x)$ is also a small polynomial. For key generation, we sample a random polynomial $a(x)$ in $R_q$, sample a noise polynomial $e(x)$, and compute $b(x) = a(x)\seckey{s(x)} + e(x) \bmod q$. We publish $(a(x), b(x))$ and keep $\seckey{s(x)}$ secret. To encrypt a plaintext polynomial $\plaintext{m(x)} \in R_q$, we sample a small polynomial $r(x)$; for intuition, you can imagine $r(x) = 1$. Then we set $c_0(x) = a(x) r(x)$ and $c_1(x) = b(x) r(x) + \Delta \, \plaintext{m(x)}$, with $\Delta = q/t$ if we embed $t$ plaintext levels. The ciphertext is $(c_0(x), c_1(x))$. To decrypt, we compute $c_1(x) - c_0(x)\seckey{s(x)}$, which cancels the $a(x)\seckey{s(x)}$ term and gives $\Delta \, \plaintext{m(x)}$ plus small noise. Dividing by $\Delta$ and rounding the coefficients recovers $\plaintext{m(x)}$. RLWE is the backbone for many modern FHE schemes.}
\end{frame}

\section{CKKS}

\begin{frame}{3. CKKS Overview}
  \begin{itemize}
    \item Approximate-number FHE supporting packed real/complex vectors (SIMD-style).
    \item Workflow: scale plaintexts by a large $\Delta$, encode integers into RLWE polynomials, then encrypt.
    \item Homomorphic addition is cheap (same scale); multiplication requires relinearization + rescale to control growth.
    \item Resulting ciphertexts keep bounded precision error, making CKKS practical for ML inference and analytics.
  \end{itemize}
  \note{Now we move to CKKS, a practical FHE scheme for approximate real and complex numbers. It is widely used for machine learning inference and data analytics. CKKS supports packed vectors, so one ciphertext can hold many values using the batching idea from earlier. The workflow is: first scale the plaintext numbers by a large factor $\Delta$, then encode the scaled integers into RLWE polynomials, and finally encrypt those polynomials. Homomorphic addition in CKKS is very cheap as long as the ciphertexts have the same scale. Homomorphic multiplication is more expensive; after multiplication we need relinearization to keep the ciphertext size small, and rescaling to control both the scale and the noise. CKKS always introduces a small approximation error, but this error can be kept within a target bound, which makes it useful in practice.}
\end{frame}

\begin{frame}{3.1 CKKS Encoding and Scaling}
  \begin{description}
    \item[Goal] Encode a real vector $(z_1, z_2, \dots, z_k)$ into the polynomial ring $R_q = \mathbb{Z}_q[x]/(x^N + 1)$ so CKKS can process it homomorphically.
    \item[Scaling] Multiply each real by a large $\Delta$ so fractional parts become big integers:
    $$
      \widetilde{\plaintext{m}} = \Delta \cdot \plaintext{m},
    $$
    because all CKKS arithmetic happens modulo $q$.
    \item[Encoding] (Same SIMD trick as Section 2.2) leverage $R_q \otimes \mathbb{C} \cong \mathbb{C}^{N/2}$ to pack the scaled vector into one polynomial—each slot stores one entry, enabling parallel processing.
    \item[Decoding] After decryption, recover the integer vector and reverse the scaling:
    $$
      \plaintext{m} \approx \frac{1}{\Delta} \cdot \widetilde{\plaintext{m}},
    $$
    yielding the original reals up to a controllable approximation error.
  \end{description}
  \note{On this slide we look at how to encode real vectors for CKKS. The goal is to move real numbers into the polynomial ring so we can encrypt them. Let the real vector be $(z_1, z_2, \dots, z_k)$. We want to encode it into the ring $R_q = \mathbb{Z}_q[x]/(x^N + 1)$ [read: “R sub q equals Z sub q of x, modulo x to the N plus one”]. First we scale the vector: multiply each real value by a large $\Delta$, so we get $\widetilde{\plaintext{m}} = \Delta \cdot \plaintext{m}$ [read: “m tilde equals Delta times m”]. After this, the fractional parts become big integers, which are safe for modular arithmetic. Second, we use the same SIMD encoding trick from before: we rely on the fact that $R_q \otimes \mathbb{C}$ is roughly $\mathbb{C}^{N/2}$, so we can pack the scaled vector into one polynomial with many slots. During decryption, we decode the polynomial back into an integer vector and then divide by $\Delta$ to get an approximation of the original real vector; the difference is the CKKS approximation error.}
\end{frame}

\begin{frame}{3.2 CKKS Encryption and Decryption}
  \begin{description}
    \item[Plaintext prep] Before encryption, scale by $\Delta$ and encode the real vector into an integer polynomial $\plaintext{m(x)}$ (Section~2.2 + 3.1).
    \item[Key generation] Identical to RLWE (Section~2.5): pick small $\seckey{s(x)}$, sample random $a(x)$ and noise $e(x)$, then publish
    $$
      b(x) = a(x) \seckey{s(x)} + e(x) \pmod{q}.
    $$
    \item[Encryption] Form ciphertext $c(x) = \bigl(c_0(x), c_1(x)\bigr)$ via
    \[
      c_0(x) = a(x) r(x), \qquad
      c_1(x) = b(x) r(x) + \Delta \, \plaintext{m(x)},
    \]
    where $r(x)$ is a fresh small polynomial.
    \item[Decryption] Subtract and divide by the recorded scale:
    \[
      c_1(x) - c_0(x)\seckey{s(x)} = \Delta \, \plaintext{m(x)} + \widetilde{e}(x)
    \]
    and compute $m(x) \approx \frac{1}{\Delta}\bigl(c_1 - c_0 \seckey{s}\bigr)$.
    \item[Scale tracking] CKKS ciphertexts explicitly store the current $\Delta$: here it records fixed-point precision (unlike RLWE’s $\Delta = q/t$ embedding) and is updated after every homomorphic operation.
  \end{description}
  \note{Here we connect CKKS to the RLWE encryption pattern. The structure is almost the same as RLWE, but we remember that the plaintext has been scaled by $\Delta$. Before encryption, we scale by $\Delta$ and encode the real vector into an integer polynomial $\plaintext{m(x)}$. Then we run RLWE key generation: choose a small secret polynomial $\seckey{s(x)}$, sample random $a(x)$ and noise $e(x)$, and compute $b(x) = a(x)\seckey{s(x)} + e(x) \bmod q$. To encrypt, we sample a small polynomial $r(x)$ and compute $c_0(x) = a(x) r(x)$ and $c_1(x) = b(x) r(x) + \Delta \, \plaintext{m(x)}$. The ciphertext is $(c_0(x), c_1(x))$. To decrypt, we compute $c_1(x) - c_0(x)\seckey{s(x)}$, which equals $\Delta \, \plaintext{m(x)}$ plus small noise; then we divide by the stored $\Delta$ to recover an approximation of $m(x)$ and decode back to real numbers. One important detail is that each CKKS ciphertext explicitly stores its current $\Delta$, and this scale changes after operations like multiplication and rescaling, so we must track it carefully to keep precision.}
\end{frame}

\begin{frame}{3.3 CKKS Rescaling and Scale Management}
  \begin{description}
    \item[Why rescale?] Ciphertexts encode scaled approximations $\plaintext{m}\cdot\Delta$. A homomorphic multiplication inflates the scale to $\Delta^2$:
    $$
      (\Delta \cdot m_0) \cdot (\Delta \cdot m_1) = \Delta^2 \cdot (m_0 m_1),
    $$
    so repeated multiplications would push the scale (and noise) out of range.
    \item[Operation] With ciphertext $c = (c_0, c_1) \in R_Q$ at scale $\Delta$ over modulus chain $Q = q_0 q_1 \dots q_L$,
    $$
      c' = \operatorname{Rescale}(c) = \left\lfloor \frac{c}{q_L} \right\rceil \bmod \frac{Q}{q_L},
    $$
    consuming the bottom modulus.
    \item[Effect] New parameters become
    $$
      \Delta' = \frac{\Delta}{q_L}, \qquad Q' = \frac{Q}{q_L},
    $$
    keeping the fixed-point scale within target bounds at the cost of one level.
  \end{description}
  \note{Now we explain rescaling, which controls the growth of the scale and the noise. Every CKKS ciphertext encodes a value as $\plaintext{m} \cdot \Delta$. When we multiply two ciphertexts, the new scale becomes $\Delta^2$. The formula on the slide is $(\Delta \cdot m_0)(\Delta \cdot m_1) = \Delta^2 \cdot (m_0 m_1)$ [read: “Delta times m zero times Delta times m one equals Delta squared times m zero times m one”]. If we keep multiplying, the scale and noise will quickly become too large. To fix this, CKKS uses a rescale operation. We think of the ciphertext as living over a modulus chain $Q = q_0 q_1 \dots q_L$. We take the ciphertext $c$ and divide it by the last modulus $q_L$, then round and drop that modulus from the chain. The slide writes this as $c' = \operatorname{Rescale}(c) = \lfloor c / q_L \rceil \bmod (Q/q_L)$ [read: “c prime equals Rescale of c equals floor of c over q sub L, modulo big Q over q sub L”]. After rescaling, the new modulus is $Q' = Q / q_L$ and the new scale is $\Delta' = \Delta / q_L$. This brings the scale back into a reasonable range. Each rescale step consumes one level in the modulus chain, so we must plan how many multiplications the circuit can afford.}
\end{frame}

\begin{frame}{3.4 CKKS Homomorphic Addition}
  \begin{description}
    \item[Component-wise sum] Ciphertexts live as pairs $(c_0, c_1)$, so addition is
    $$
      (c_0, c_1) + (c'_0, c'_1) = (c_0 + c'_0,\; c_1 + c'_1),
    $$
    preserving the decrypted quantity $c_1 - c_0 \seckey{s}$ slot-wise.
    \item[Scale alignment] Addition requires both operands to share the same stored scale $\Delta$; if not, rescale one ciphertext first (Section~3.3) to keep fixed-point alignment.
    \item[Effect on noise] The scale remains unchanged and noise growth is negligible, so this is CKKS’s cheapest, most stable homomorphic primitive.
  \end{description}
  \note{Now we look at homomorphic addition in CKKS, which is very simple. Each ciphertext is a pair $(c_0, c_1)$. To add two ciphertexts we just add them component-wise: $(c_0, c_1) + (c'_0, c'_1) = (c_0 + c'_0, c_1 + c'_1)$ [read: “c zero, c one plus c zero prime, c one prime equals c zero plus c zero prime, and c one plus c one prime”]. Because decryption uses $c_1 - c_0 \seckey{s}$, the decrypted value of the sum is just the sum of the underlying scaled plaintexts, slot by slot. There is one condition: the two ciphertexts must have the same scale $\Delta$. If their scales are different, we rescale one of them first so they match. Once the scales are aligned, addition does not change the scale and only adds a tiny bit of noise. So addition is the cheapest and most stable operation in CKKS; it is almost free compared with multiplication.}
\end{frame}

\begin{frame}{3.5 CKKS Homomorphic Multiplication and Relinearization}
  \begin{description}
    \item[Multiplication result] Each ciphertext decrypts as $c_1 - c_0 \seckey{s} \approx \Delta \cdot \plaintext{m}$. Multiplying two ciphertexts therefore expands
    $$
      (c_1 - c_0 \seckey{s}) (c'_1 - c'_0 \seckey{s}) =
      d_0 + d_1 \seckey{s} + d_2 \seckey{s}^2,
    $$
    where
    \[
      d_0 = c_1 c'_1,\quad
      d_1 = -(c_1 c'_0 + c_0 c'_1),\quad
      d_2 = c_0 c'_0.
    \]
    \item[Why relinearize] The appearance of the $d_2 \seckey{s}^2$ term enlarges the ciphertext (now $(d_0, d_1, d_2)$) and would require the secret key squared to decrypt, increasing storage and computation.
    \item[Relinearization] Apply the evaluation key $\mathrm{EvalKey}(s^2)$ to fold the $d_2 \seckey{s}^2$ contribution back into the two-term format:
    \[
      (c_0, c_1) \times (c'_0, c'_1)
      \xrightarrow{\text{multiply}}
      (d_0, d_1, d_2)
      \xrightarrow[\text{remove } d_2 (s^2)]{\text{relinearize}}
      (e_0, e_1).
    \]
    \item[Reference] CKKS paper (Cheon--Kim--Kim--Song, ASIACRYPT~2017).\footnote{Cheon, Kim, Kim, Song, “Homomorphic Encryption for Arithmetic of Approximate Numbers,” ASIACRYPT 2017.}
  \end{description}
  \note{Now we look at homomorphic multiplication, which is more involved. Recall that a CKKS ciphertext decrypts as $c_1 - c_0 \seckey{s} \approx \Delta \cdot \plaintext{m}$ [read: “c one minus c zero times s is approximately Delta times m”]. If we multiply two ciphertexts, we multiply these decrypted forms. The slide shows $(c_1 - c_0 \seckey{s})(c'_1 - c'_0 \seckey{s}) = d_0 + d_1 \seckey{s} + d_2 \seckey{s}^2$, with $d_0 = c_1 c'_1$, $d_1 = -(c_1 c'_0 + c_0 c'_1)$, and $d_2 = c_0 c'_0$. So the result depends on both $\seckey{s}$ and $\seckey{s}^2$. This means the new ciphertext has three components $(d_0, d_1, d_2)$ and would require knowledge of $\seckey{s}^2$ to decrypt. If we keep multiplying without fixing this, ciphertext size and key operations would grow a lot. Relinearization solves this problem. We use a special evaluation key, which encrypts $\seckey{s}^2$, to fold the $d_2 \seckey{s}^2$ term back into the first two components. The diagram shows $(c_0, c_1)$ times $(c'_0, c'_1)$ mapping to $(d_0, d_1, d_2)$ and then to $(e_0, e_1)$ after relinearization. The final ciphertext $(e_0, e_1)$ decrypts with the original secret key $\seckey{s}$. In practice we do multiplication, then relinearization, and then usually rescaling to control the scale.}
\end{frame}

\section{TFHE}

\begin{frame}{4. TFHE Overview}
  \begin{description}
    \item[Computation model] TFHE operates on encrypted bits; each Boolean value is packed into a (T)LWE sample, unlike CKKS’s approximate real vectors.
    \item[Encryption layer] LWE-style keys/encapsulation; with $r = \mathbf{1}$ and $m \in \{0,1\}$:
    $$c = (c_0, c_1) = \bigl(A,\, A\seckey{s} + \mu \plaintext{m} + e\bigr),$$
    where $\mu$ (typically $q/2$) plays the role of the LWE scaling factor $\Delta$.
    \item[Logic gates] Supports homomorphic AND/XOR/NOT primitives, making it ideal for comparisons, branching, verification, and encrypted control flow.
    \item[Bootstrapping] Every gate invocation bootstraps away noise, allowing arbitrarily deep Boolean circuits with stable precision.
    \item[Contrast to CKKS] CKKS excels at numeric workloads but struggles with exact branching or comparisons; TFHE provides the complementary bit-level toolkit.
  \end{description}
  \note{Now we switch from CKKS to TFHE. TFHE works with encrypted bits instead of approximate real numbers. In TFHE, each Boolean value $\plaintext{m} \in \{0,1\}$ is encrypted as an LWE-style sample. The slide shows $c = (c_0, c_1) = (A, A\seckey{s} + \mu \plaintext{m} + e)$ [read: “c equals c zero, c one equals big A, and A times s plus mu times m plus e”]. Here $\mu$ is a scaling factor, usually $q/2$, similar to $\Delta$ in LWE. TFHE supports homomorphic logic gates like AND, XOR, and NOT, which makes it very good for comparisons, conditional branches, and verification tasks. It is the opposite of CKKS: CKKS is great for numeric workloads but has trouble with exact branching and comparisons, while TFHE is designed for these bit-level operations. The most important feature is fast bootstrapping: each gate call can include bootstrapping that refreshes the noise, allowing deep Boolean circuits without losing correctness.}
\end{frame}

\begin{frame}{4.1 TFHE Gate Operations}
  \begin{description}
    \item[Ciphertext form] Encrypt each bit $\plaintext{m} \in \{0,1\}$ as $c = (A, c_1)$ with $c_1 = A\seckey{s} + \mu \plaintext{m} + e$.
    \item[NOT gate] Flip the phase to encode $1 - \plaintext{m}$; equivalently $c_1' = A\seckey{s} + \mu (1 - \plaintext{m}) + e$:
    $$\text{NOT}(c) = \bigl(-A,\; \mu - c_1\bigr) \bmod q.$$
    \item[XOR gate] Homomorphic addition implements XOR:
    $$\text{XOR}(c_0, c_1) = c_0 + c_1 \pmod{q}.$$
    \item[AND challenge] Multiplicative gates inflate scale/noise since
    $$
      (\plaintext{m}_0 \mu)(\plaintext{m}_1 \mu) = (\plaintext{m}_0 \plaintext{m}_1) \mu^2,
    $$
    so TFHE uses bootstrapping to refresh ciphertexts after AND/NAND.
  \end{description}
  \note{Next we look at some basic gate operations in TFHE and how NOT, XOR, and AND behave on encrypted bits. Each ciphertext encrypts a bit $\plaintext{m} \in \{0,1\}$ as $(A, c_1)$ with $c_1 = A \seckey{s} + \mu \plaintext{m} + e$. For the NOT gate, the output should encrypt $1 - \plaintext{m}$. We use the identity $(1 - \plaintext{m})\mu = \mu - \plaintext{m}\mu$. The slide writes $\text{NOT}(c) = (-A, \mu - c_1) \bmod q$ [read: “N O T of c equals minus A, mu minus c one, modulo q”]. This effectively flips the phase. For the XOR gate, homomorphic addition is enough, so the slide writes $\text{XOR}(c_0, c_1) = c_0 + c_1 \pmod{q}$ [read: “X O R of c zero and c one equals c zero plus c one, modulo q”]. This works because XOR is like addition modulo 2 and the structure is linear. For AND and NAND, multiplying ciphertexts scales the phase by $\mu^2$. The slide shows $(\plaintext{m}_0 \mu)(\plaintext{m}_1 \mu) = (\plaintext{m}_0 \plaintext{m}_1) \mu^2$ [read: “m zero times mu times m one times mu equals m zero times m one times mu squared”]. This increases scale and noise, so TFHE uses bootstrapping after AND or NAND gates to refresh the ciphertext.}
\end{frame}

\begin{frame}{4.2 TFHE Programmable Bootstrapping (PBS)}
  \begin{description}
    \item[Phase encoding] Each ciphertext hides a phase $\phi \approx \mu \plaintext{m}$ (with $\mu \approx q/4$): $\phi \approx 0$ encodes $\plaintext{m}=0$, $\phi \approx \mu$ encodes $\plaintext{m}=1$.
    \item[Bootstrapping goal] Extract the phase homomorphically, evaluate a function on it, and re-encode a fresh low-noise ciphertext without decrypting.
    \item[PBS view] Treat bootstrapping as Decode $\rightarrow$ Evaluate $\rightarrow$ Re-encrypt inside the ciphertext, guided by a bootstrapping key.
  \end{description}
  \note{Now we move to programmable bootstrapping, or PBS, in TFHE. PBS is what keeps TFHE powerful for deep Boolean circuits. Each TLWE ciphertext hides a phase value $\phi$ that is close to either $0$ or $\mu$. If $\phi$ is near $0$, it encodes bit $0$; if $\phi$ is near $\mu$, it encodes bit $1$. The goal of bootstrapping is to extract this phase homomorphically, apply some Boolean function $f$ to it, and then re-encrypt a fresh ciphertext with low noise, all without decrypting in the clear. Conceptually, PBS performs three steps under encryption: decode the phase, evaluate the function, and re-encrypt the result. Because the function is programmable, we can implement many different gates and small lookup tables with PBS.}
\end{frame}

\begin{frame}{4.2 TFHE Programmable Bootstrapping (PBS)}
  \begin{description}
    \item[Phase reconstruction] Begin with $\phi = c_1 - A\seckey{s}$; instead of exposing \seckey{s}, compute
    $$
      \Enc(\phi) = \Enc(c_1 - A\seckey{s}).
    $$
    \item[Need for $\Enc(A\seckey{s})$] Since $A\seckey{s} = \sum_{i=1}^n a_i s_i$,
    $$
      \sum_{i=1}^{n} a_i \cdot \Enc_{\mathrm{GLWE}}(s_i)
      = \Enc\!\left(\sum_{i=1}^n a_i s_i\right)
      = \Enc(A\seckey{s}),
    $$
    enabling phase recovery without revealing \seckey{s}.
    \item[Bootstrapping key] Publish the GLWE encryptions of the secret coefficients:
    $$
      \mathrm{BK} = \{\Enc_{\mathrm{GLWE}}(s_1), \ldots, \Enc_{\mathrm{GLWE}}(s_n)\},
    $$
    so PBS has the encrypted ingredients needed to refresh ciphertexts safely.
  \end{description}
  \note{Now we zoom in on the first technical step: phase reconstruction. We want to recover the phase $\phi$ in encrypted form. The phase is $\phi = c_1 - A\seckey{s}$ [read: “phi equals c one minus A times s”]. We cannot compute this directly, because that would reveal the secret key $\seckey{s}$. Instead, we aim for an encryption of $\phi$, written as $\Enc(\phi)$. The slide shows $\Enc(\phi) = \Enc(c_1 - A\seckey{s})$, so we need an encryption of $A\seckey{s}$. Note that $A\seckey{s} = \sum_{i=1}^n a_i s_i$. If we publish encryptions of each secret coefficient $s_i$ under GLWE, we can compute $\sum_{i=1}^{n} a_i \cdot \Enc_{\mathrm{GLWE}}(s_i) = \Enc(A\seckey{s})$ [read: “sum from i equals one to n of a i times Enc G L W E of s i equals Enc of A times s”]. These encryptions of the secret coefficients form the bootstrapping key, written as $\mathrm{BK}$. With $\mathrm{BK}$, PBS can reconstruct the phase in encrypted form without ever exposing the secret key.}
\end{frame}

\begin{frame}{4.2 TFHE Programmable Bootstrapping (PBS)}
  \begin{description}
    \item[Encrypted phase] Using the previous step we carry forward $\Enc(\phi) = \Enc(c_1 - A\seckey{s})$.
    \item[Programmable goal] Map $\phi$ through $f$ so $\Enc(\phi) \rightarrow \Enc(f(b))$.
    \item[Gadget decomposition] Produce weights via
    $$
      \mathrm{GadgetDecomp}\bigl(c = \Enc(\phi)\bigr) = (w_0, w_1, \dots, w_k),
    $$
    which form the encrypted selection signals.
    \item[LUT for $f$] Store encrypted outputs
    $$
      \mathrm{LUT}_f = (\Enc(f(0)),\; \Enc(f(1))),
    $$
    generalized to higher arity as needed.
    \item[External product] Combine weights and LUT to obtain the refreshed ciphertext:
    $$
      \Enc(f(b)) = \mathrm{LUT}_f \bigstar (w_0, \dots, w_k)
      = \sum_{i=0}^{k} w_i \cdot \mathrm{LUT}_f^{(i)}.
    $$
    Here each $w_i$ acts as an encrypted selection weight and $\mathrm{LUT}_f^{(i)}$ stores the encrypted function value.
  \end{description}
  \note{Finally, we see how PBS applies the function $f$ and finishes the refresh. We start from an encrypted phase $\Enc(\phi)$ and want an encryption of $f(b)$, where $b$ is the underlying bit. First, we use gadget decomposition, which is a standard trick in lattice cryptography. We decompose the ciphertext into a tuple of weights $(w_0, w_1, \dots, w_k)$; the slide writes this as $\mathrm{GadgetDecomp}(c = \Enc(\phi)) = (w_0, w_1, \dots, w_k)$. These weights act as encrypted selection signals. Second, we prepare a look-up table, or LUT, for the function $f$. For a single bit, the LUT is $\mathrm{LUT}_f = (\Enc(f(0)), \Enc(f(1)))$, and we can generalize this idea for more inputs. Third, we compute an external product between the weights and the LUT. The slide writes $\Enc(f(b)) = \mathrm{LUT}_f \bigstar (w_0, \dots, w_k) = \sum_{i=0}^{k} w_i \cdot \mathrm{LUT}_f^{(i)}$ [read: “Enc of f of b equals L U T sub f star of the tuple w zero to w k equals the sum over i of w i times L U T sub f to the i”]. Each $w_i$ selects part of the encrypted function value. The result is a fresh ciphertext that encrypts $f(b)$ with low noise. Because we can precompute $\mathrm{LUT}_f$ for many functions, PBS is called programmable bootstrapping.}
\end{frame}
